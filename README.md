# 集运管理系统（速捷盛 SJSCM · 后端）

> 跨境电商集运（代购/转运）业务的全栈管理系统后端。本仓库为**脱敏开源版**，已移除服务器地址、密码哈希、密钥等敏感信息，仅保留可公开的业务逻辑与架构设计，供技术交流与简历展示。

## 一、项目简介

面向「中国 → 海外（以工业市/欧美华人为例）」集运场景：客户把多个电商包裹寄到集运仓，仓库按**邮编**建批次、拼箱、计费、发货。系统要同时服务：**仓库管理端（Web）** 与 **客户小程序（微信）** 两端。

核心业务流（周循环）：
1. 周一~周三：包裹陆续入库（incoming）
2. 周三下午：按邮编建批次（batch），同邮编同时仅一个未锁定批次
3. 客户确认发货意向 → 待打包
4. 周四~周六：打包（packed）→ 合箱（carton）→ 装货清单 → 派发账单 → 发货
5. 客户也可「攒着不发」或走 VIP 单独地址自送

## 二、技术栈

- **Web 框架**：Flask 2.x + Werkzeug
- **ORM**：SQLAlchemy 2.0（声明式模型 `models.py`）
- **模板**：Jinja2（仓库管理端页面 `templates/`）
- **数据库**：SQLite（生产环境单文件 `consolidation.db`，约 2.1 万入库单 + 3800 打包箱）
- **小程序后端**：`wechat/wechat_api.py`（独立 Flask 服务 :5005，云签名信任模式）
- **安全代理**：微信云函数 `sjsApi` 对 openid 做 HMAC-SHA256 签名，服务端 `WX_CLOUD_TRUST=1` 只认签名

## 四、核心业务模型

| 概念 | 说明 |
|------|------|
| 客户 customer | 普通客户 / VIP 客户（可走单独地址自送） |
| 入仓包裹 incoming_package | 入库单，含单号、性质（普/敏）、货位、批次归属 |
| 批次 batch | 按邮编归集的发货批次，**箱 ↔ 包裹** 多对多 |
| 打包箱 packed_package | 实际发货箱，含计费重、运费 |
| 合箱 carton / carton_item | 多个包裹装入一个大箱 |
| 运费 freight | 按客户 × 普/敏 维度计费，可手动覆盖 |

**运费计算口径（全系统唯一真相源 `_is_sensitive`）**：
- 计费重 = `ceil0.5(max(体积重, 实重, 1kg))`（向上进位 0.5kg）
- 普货 ¥25/kg，敏货 ¥35/kg
- 已结算（`freight_settled=1`）排除出待付
- 手动计费重覆盖表 `batch_freight_override`（客户 × 普/敏粒度）

## 五、鉴权模型

管理端采用 **白名单即管理员** 机制：`WX_ADMIN_OPENIDS` 环境变量存 openid 列表，**无密码二重验证**。客户端请求经云函数签名后，服务端校验签名与白名单。

## 六、重大漏洞与修复（技术亮点）

> 以下为项目推进过程中遇到并修复的真实高影响问题，反映对**数据建模、前后端联动、计费一致性**的把控。

### 漏洞 1：批次单号严重漏统计（数据建模 Bug，影响对账）

- **现象**：某批次（如 125 批）在导出时只有 37 个包裹，实际应有 700+。
- **根因**：包裹的「发货批次」不能看 `incoming_packages.batch_id`（那是**入仓批次**，合箱/拼单后与实际发货批次不一致）。真正的归属在 `PackedPackageItem` 表（箱 ↔ 包裹的多对多关联）。125 批的 139 个打包箱经该表关联了 **732 个入仓包裹**，其中 696 个入仓时归到别的批次，但发货时合进了 125 批。
- **修复**：导出/统计改为以 `PackedPackageItem → packed_packages.batch_id` 还原真实发货批次，并补「所在箱号」「入仓批次号」两列。批次 sheet 由 77 个补齐到 103 个（含 26 个「只有打包箱、没有入仓批次」的批次）。
- **验证**：125 批现 732 行，与数据库实查完全一致；全表 2.1 万单号无遗漏无重复。

### 漏洞 2：计费明细下标错位导致改错客户计费（前端 Bug）

- **现象**：管理端「批次账单」里修改某客户计费重后，保存却改到了另一个客户身上。
- **根因**：`batch-bill.js` 用 `wx:for="{{filteredItems}}"` 遍历（筛选后可见列表），绑定 `data-idx` 为可见下标；但 JS 读写却用该 `idx` 去操作 `this.data.items[idx]`（全量数组）。筛选后两者下标错位，导致写错条目。同时误读了 `res.effective`（实为 `res.chargeable`）。
- **修复**：新增 `_realIdx(cid)` 用客户 ID 反查真实条目；wxml 改为 `data-cid`；修正误读字段。
- **验证**：多选客户、筛选后逐一改计费重，落库均正确。

### 漏洞 3：运费孤儿表 `freight_records.carton_id` 全 NULL（设计缺陷）

- **现象**：库中存在 511 条运费记录、金额合计约 ¥9 万，但无法关联到任何批次/箱。
- **根因**：历史遗留表中 `carton_id` 字段从未被写入（始终 NULL），导致该表与业务脱节，无法用于对账。
- **修复**：计费/账单改为基于 `packed_packages` 的**实时计算**（与小程序前端口径一致），并保留手动覆盖机制；该 legacy 表明确标记为「不参与当前计费」。
- **影响**：避免了依赖一张死表导致运费大面积错误。

### 漏洞 4：拼单跨批次不更新 `batch_id`（已知缺陷，已加校验）

- **现象**：两客户拼单时，若跨了批次，包裹的 `batch_id` 未同步更新，导致包裹被错误归集。
- **修复**：在拼单逻辑中增加批次一致性校验，历史 4 条异常数据已定位并补校验规则。

### 漏洞 5：管理端鉴权重构——白名单即管理员

- **现象**：原设计有密码二重验证，但管理员账号与微信 openid 强绑定，密码环节冗余且易成攻击面。
- **修复**：下线密码二重验证，改为 `WX_ADMIN_OPENIDS` 白名单 + 云函数签名信任（`WX_CLOUD_TRUST=1`）。非白名单请求直接返回 40003；批次锁定/解锁仅系统端可用，小程序端拒绝。
- **收益**：攻击面收敛，且天然防止客户端伪造身份（openid 由微信服务端下发，前端拿不到）。

### 漏洞 6：运费敏感性判定散落（一致性隐患）

- **现象**：多处用 `nature` 字符串判断是否敏货，判断逻辑不统一，易漏判。
- **修复**：抽离唯一函数 `_is_sensitive(nature)`：`'敏' in nature` 或英文 `sensitive/ming`，全系统统一调用，杜绝散落判断。

## 七、部署说明（脱敏）

生产环境为单台 Linux 服务器，通过 systemd 托管两个服务：
- `consolidation`（主应用，:5000）
- `consolidation-wechat`（小程序后端，:5005，nginx :80 的 `/wechat/` 反代到 5005）

密钥（服务器 IP、管理员密码哈希、微信 AppSecret、云函数密钥等）均通过环境变量注入，**不入库、不入代码**。本仓库已全部以占位符 `<...>` 替换。
